Introduction

Software requirements are fundamental for the successful realization of a complex application. They have multiple roles.

  1. Requirements define what the functionality the end product should provide.
  2. Requirements can be prioritized. The project leader can decide which functions will be available in a planned release.
  3. Requirements are the reference to define the acceptance tests for an application. They define the contract the product manager expects to be fulfilled.
  4. They focus the development team. The list of high priority requirements show that the application must in any cases be able to perform.

A functional software requirement should have a set of attributes.

  • A requirement is clear, complete and do not contain contradiction.
  • A requirement should be realizable.
  • A requirement should be testable.

A non functional requirement has also a set of attribute.

  • A requirement is clear, complete and do not contain contradiction.
  • A requirement should be measurable. The minimum, optimum and maximum measured values should be defined before starting to measure.

Risks

Risk analysis helps the development team to maximize the probability project success. The experiences collected during the development and use of the ancestor of pmMDA ancestor. Additional potential problems were identified through the Delphi Oracle method. The following list of risks were identified during the inception phase of the project pmMDA.

    Lack of development resources
    The actual development team is quite small and has only spare resources to allocate for the development of pmMDA. The risk is high based on documented facts about various open projects. Managerial effort will be invested to receive resources from commercial projects using pmMDA product and support so part of the development.
    Too wide scope
    The goals of the project are too ambituous. This risk is dependent of the risk "Lack of development resources" and is medium. Managerial effort will be invested to attract new developers on the project.
    Lack of adequacy
    The pmMDA application does not fulfill real needs. This risk is minor based on experience when developing industrial and commercial applications. The OMG efforts consolidate this assumption.
    Wrong technologies
    The selected technologies are the wrong ones or miss the market. The application is based on open standards. These standards are already accepted as state of the industry. The risk is low.

Initial Planning

The initial prototype in Java was written during Spring 2003. The prototype was used to generate the complete business layer and CORBA transmission layer of a distributed contracts management application. This version is considered as the 0.0.

The prototype will be refactored and documented. This source code base can be used to add new funtions or used to write technical university semester projects. This version is the 0.1 and should be available end of September 2003.
