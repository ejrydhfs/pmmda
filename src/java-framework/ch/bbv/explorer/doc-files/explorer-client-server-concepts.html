Introduction

Distributed applications are almost all built with the same architecture. Administrative applications with a small amount of concurrent users are build as two tiers architectures. These applications are management consoles, interface to other systems, and power user enhanced clients. Regular client applications have a greated number of concurrent users and need a three tiers architecture.

The advantage of our framework is its strong capabilities to manipulate graphs of objects. This concept is supported in the server, the transfer layer, the client application and the support functions such as reporting or printing.

Business Layer

The classes part of the business layer follow the Java bean conventions. A property can be read or written. If desired a property is changeable and vetoable. The framework adds an internal flag indicating if an object was modified. This information is used to minimize the number of updates in the database. A fundamental fact is that the business layer in the client and server is based on the same classes. No difference exists for the software. Therefore functions can be moved between server and client without modifications.

The clone status is deduced from the framework operations workflow and does not need to be explicit. A new object is recognized because its identifier is null. A deleted object is infered because it is missing in the reference graph of business objects.

The framework also provides an implementation of the visitor pattern to simplify the implementation of traversal algorithms. A specialized functor version of the visitor interface reduces the amount of coding for simple operations on all nodes of the graph.

Two Tiers Architecture

Server Cache

The impendance mismatch between relational database and object-oriented application is solved with mapping tools. The architecture uses standard compliant based on open source frameworks. The supported standard are ODMG and JDO. The used project is OJB. This component supports native caching mechanisms. Small applications should use the internal global or thread caches. More complex applications should use the cache implementing JSR-107. The implementation of the Turbine project is natively supported in OJB. This cache technology supports tuning of cache parameters for a specific pattern of usage.

Reference Code Cache

Commercial applications uses reference codes to streamline input data and support different wordings often used in different countries or business cultures. The refence code service manages its local cache of all often used codes to speed-up interface responsiveness, in particular user interface respensiveness. Remote clients duplicates this cache locally to avoid network traffic.

Optimistic Locking

Multiple clients often read the data and seldom update it. Optimistic locking is ideal for such a constellation. The framework uses per default optimistic locking to detect concurrent changes.

Administrative tools used to perform Extract Transform Load processes should not use optimistic locking but simple pessimistic transaction to diminish the number of created transactions to perform such a job.

Queries

Queries can be quite complex or return many matches. Such queries are difficult to program in the business object layer and are often not efficient. A mechanism must be provided to define complex queries and run efficiently the query. The ODMG OQL language is used to retrieve data. In special cases query by criteria can also be used but they are not standardized.

Manipulation of a lightweight partial view of the business object model should not be implemented through queries but through the definition of an OJB model describing the business view.

Three Tiers Architecture

Client Cache

The client should cache complex data and reference codes locally to diminish network traffic and enhance the responsiveness of the user interface. Distributed applications are not always connected through a local area network. The round trip delay cannot be ignored. More complex clients should use caches implementing JSR-107.This cache technology supports tuning of cache parameters for a specific pattern of usage.

Reference Code Cache

All often reference codes are cached locally. The cache is persisted locally to speed up start-up time of the client. Ingeneous mechanisms are provided to detect an update of the code values and load them from the server when needed. The serialized file is stored in a configurable directory.

Optimistic Locking

The server and client uses per default optimistic locking. Upon sucessful store of the modified data, only minimal information is sent back to the client to minimize network traffic. Often the data is only the new timestamps used for the optimistic locking, identifiers for newly inserted objects and optionally small set of information generated on the server side.

Communication to the Server

THe communication to the server uses always services available from public service components. The architecture respects the SOA guidelines.

Derived Attributes

Derived attributes are values computed from other attributes. Derived computation often implements business logic. Derived attributes are calculated in two situations. First the user updates an attribute. All depending attributes must be recomputed to reflect changes on the interface. Second data is migrated from other systems. One of the final step of the load process is the computation of all derived attributes. Both mechanisms are needed in any real world application.

The first mechanism is implemented using the value changed event of a property. The change triggers the registered business server, which can apply the computation rules using the changed property. Care is needed to avoid cyclic dependencies in the business rules. The rules can always be written so that all dependent attributes are leaves in the dependency graph.

The second mechanism is implemented as a visitor service used to compute all derived attributes of a subgraph. The visitor calls the same computation rules defined for the first mechanism.

Evolution

Experience with the framework showed that the cloned flag is superfluous. The flow of operations always allows us to decide if a graph is the original one or a copy. The differences between the orginal and the copied graph need only to be infered on sever side. Therefore no communication overhead exist when transmitting the changes to the server. The copied graph is simply send to the server.

If the user only edited properties and did not alter the topology of the graph, you can use the shallow operations to optimize the communication overhead. The generated business objects should contain convenience methods to update the properties in the reference object.
