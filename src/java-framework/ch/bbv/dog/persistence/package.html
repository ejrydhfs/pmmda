The business object graph persistence provides a layer to store graphs in a relational database.

Introduction

The business object graph persistency layer is implemented with the help of the open source framework object Java bridge OJB. from the Apache group. This personality is well tested and mature enough for productive environment. An abstraction layer is provided to hide all specific features of OJB ODMG. The motivation is to move later to the JDO personality without requiring changes in the source code of the application using our framework.

The architecture foresees that transaction contexts are managed at the service level. This assumption enables to define the granularity of a transaction so that the database is always in a consistent state.

A major goal of the architecture is to support various personalities such as ODMG, API broker and JDO.

Cache Handling

It is necessary to programmatically manage the content of the OJB cache because OJB is not aware that the business object graphs the framework manipulates are copies and not the ones stored in the cache. The following algorithm is implemented.

  1. A request to save a business object graph is received.
  2. The OJB cache is cleaned from all objects with the same identifier currently cached.
  3. The received business object graph is stored in the database. Removed objects are deleted, new objects are inserted, and modified ones are updated.The persistence layer adds all these objects in its cache.
  4. If the transaction is rolled back, the received objects are removed from the cache because they do not reflect the values stored in the database.

The framework works only correctly if one threat at a time performs an update. The client must implement its own synchronization mechanisms. Two solutions are feasible. A cache exists on a per thread basis. The client implement mutual exclusion on the common cache.

Helper Classes

Most of the work is programmed in function objects. This approach build on the features available in the business objects and is extremely efficient to implement.

    Swap Object in Cache
    Removes the object with the same identifier from the cache and inserts the new one in the cache.
    Collect Store Changes
    The functor collects the administrative information of all updated objects. An updated object is identified by its flag modified set to true. For each such an object an associated business object update instance is created. At the end the flag modified is reset to false.
    Collect Objects
    Collects all objects. This is quite a trivial functor.

Open Points

The provided implementation handles internally the transactional context when interacting with the database. Business logic sometimes needs more control on the transaction. Currently control could be implemented using nested transactions in non-managed environments and taking over control of transactional context in managed environments.
